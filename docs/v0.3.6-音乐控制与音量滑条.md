## 二、音乐控制：QQ 音乐只肯读、不肯收

### 现象

`TryPlayAsync/TryPauseAsync` **调用成功**，但 QQ 音乐的状态纹丝不动；
真实媒体键却能立刻控制。

### 修法

1. helper 先发 SMTC 命令 → **等 600ms 看状态到底变没变** → 没变就**补发全局媒体键**
   （`keybd_event` 发 `VK_MEDIA_PLAY_PAUSE` / `0xB0` / `0xB1`）；
2. 回执里的 `ok` 改成**"真的生效了"**，并带 `via`（smtc / mediaKey / noop）；
3. **已经是目标状态就不发**（别让「点暂停」把暂停中的音乐点成播放）。

### 拔掉乐观更新（这条是用户看到的"点了没反应"的真正原因）

以前：收到 `ok:true` 就把按钮切成"暂停" —— 看着像点动了，其实音乐没停。
现在：点了先进入**过渡态**（`media.pending`），等**真实状态**回流才换图标；
400ms 还没回来就恢复原样。

### 一个必须写进文档的限制

**媒体键是全局的**：同时有别的播放器在放时，这一下可能打到别人身上。
这是 Windows 的机制，不是我们的 bug。

## 三、系统音量：手写 COM 互操作

`IAudioEndpointVolume` 是 Win32 COM，.NET 的 WinRT 投影里没有它；
NAudio 那类封装要拉 NuGet（离线环境装不稳）→ **手写 `[ComImport]` 声明**。

### 坑 1：接口方法的声明顺序就是 COM vtable 的顺序

改顺序 = 调错方法。

### 坑 2：**返回值会骗人**

| 现象 | 真相 |
|---|---|
| `SetMasterVolumeLevelScalar` 返回 `S_FALSE(1)` | 按文档传 `GUID.Empty` 就是这样 —— **算成功** |
| 同一方法返回 `ERROR_NOT_FOUND(0x80070490)` | **但音量真的改了**（读回就是目标值） |

**所以判定改成「设完再读回来比对」—— 以事实为准，不以返回码为准。**
（第一版按 `hr == 0` 判失败，把"明明设成功了"报成失败，差点当成 bug。）

### 坑 3：`IAudioEndpointVolumeCallback` 这条路在 Win10+ 上走不通

规格要求"外部按音量键时滑条要跟手，用 `IAudioEndpointVolumeCallback`，别靠轮询"。
实测：

```
QueryInterface(IConnectionPoint)         hr=0x80004002 (E_NOINTERFACE)
QueryInterface(IConnectionPointContainer) hr=0x80004002 (E_NOINTERFACE)
```

**Win10+ 的默认端点不暴露 COM 连接点**，回调注册不上（NAudio 在 Win10 上同样收不到）。
连原生 vtable 的 QueryInterface（绕开 .NET RCW 的接口隔离）也是同样结果。

**退路**：**200ms 轮询**一次 `GetMasterVolumeLevelScalar`（开销可忽略），
外部按音量键后最多 200ms 滑条跟上。
拖滑条时是**界面本地先动**，不等这个轮询，所以拖动本身是跟手的。

### 坑 4：没开音乐软件时，SMTC 会**挂死**

`GlobalSystemMediaTransportControlsSessionManager.RequestAsync()` 在没有会话时可能一直不返回，
实测把整个 watch 循环卡住，连音量这种跟 SMTC 无关的功能都被拖死。

**修法**：
- SMTC 调用加 **3 秒超时**（超时按"没有会话"处理，音乐行藏掉）；
- **音量通道与 SMTC 主循环解耦**：音量先推、单独跑，不等会话。

## 四、音量滑条

### 交互（按肥鱼的规格）

- 音乐行右侧一个喇叭图标 → 点它把**歌名区换成滑条**（行高不变）；
- 轨道 4px、拇指 12px；滚轮 ±5%；拖完 3 秒不动或点岛的其他地方自动收起；
- 拖动节流 50ms，**松手必须落最终值**；
- `volumeOk=false`（拿不到音量 / 没有音频设备）→ **整个音量入口隐藏**，不显示假的 0。

### 坑 5：尺寸变量和颜色变量**同名**（连踩两次）

`--island-vol-track` 既是**轨道高度**（4px）又是**轨道颜色**（主题里定义）——
同名被主题文件覆盖，**轨道高度实测变 0、拇指尺寸变 0**。
现在尺寸一律带尺寸后缀：`--island-vol-track-h` / `--island-vol-thumb-size`。

### 坑 6：~~这块浮层上，React 的 mouse/pointer 事件不触发~~（**结论已推翻**）

原来记的是：原生 `addEventListener('mousedown'/'mousemove'/'mouseup')` **收得到事件**，
但 React 的 `onMouseDown/onMouseMove/onMouseUp` **不触发**（`onWheel` 是好的）；
合成事件也一样。原因当时没查清，于是把滑条的事件改用**原生监听**绑。

> ⚠ **2026-11-24 上午更正**：这条**不是问题**。
> 现在 `VolumeSlider.tsx` 用的是 React 的 **pointer 事件 + `setPointerCapture`**，
> 真机拖动实测**每一步都跟上**（见第四节之二）。
> 之前"拖动不跟手"的真正原因在 helper 那边（坑 7），跟 React 无关。
> 「原生监听比 React 可靠」这个结论是错的 —— 真机指针事件走的就是原生路径，
> React 只是转发，pointer capture 一样生效。

### 坑 7：**音量通道被 SMTC 通道堵住**（拖动不跟手的真因）

**现象**：拇指跟着走、界面音量也变，但**系统真值一直卡在第一次的值**。

实测（2026-11-24 上午，用独立进程读系统真值）：

```
移到 60% → 拇指=60% 主进程音量=60 系统真值=80   ← 真值没动
移到 40% → 拇指=40% 主进程音量=40 系统真值=80
```

**根因**（`tools/smtc/Program.cs` 的 watch 循环）：

```
读循环 → 处理命令 → await StateLineAsync() → 处理下一条
```

`StateLineAsync()` 要走 SMTC（`RequestAsync`），而**没开音乐软件时它会挂到 3 秒超时**。
于是每条命令之间隔了 3 秒 —— 音量命令排在后面全堵住了。

**修法**：

- 音量命令（`vol <n>`）**就地处理**（纯 COM 调用，毫秒级），不等媒体状态刷新；
- 媒体命令（play/pause/next/prev）**丢到另一条通道**慢慢办，不占着读循环；
- 音量命令后只推 `kind=volume` 行。

**修完之后**：

```
移到 60% → 拇指=60% 主进程音量=60 系统真值=60
移到 40% → 拇指=40% 主进程音量=40 系统真值=40
移到 20% → 拇指=20% 主进程音量=20 系统真值=20
移到 10% → 拇指=10% 主进程音量=10 系统真值=10
```

### 坑 8：真机鼠标的坐标体系 —— `SetCursorPos` 吃 **DIP**，不是物理像素

这台机器 150% 缩放。之前按「SetCursorPos 要物理像素」把坐标乘了 1.5，
**鼠标一直落在屏幕的别处**，岛收不到 hover、滑条拖不动。

实测（`scripts/probe-cursor-scale.mjs`）：

```
按 DIP 直接传      → 传给 SetCursorPos (378,12)  展开=true  hover=true
按物理像素传(×1.5) → 传给 SetCursorPos (567,18)  展开=false hover=false
```

> **2026-11-23 深夜"真机拖动测不出来"的真正原因就在这里**，不是产品的问题。
> 当时没有证据就写成"CDP 怪癖"，差点变成一个假的 bug。

### 坑 9：鼠标已经在岛上时，不会再发 mouseenter

CSS 的 `:hover` 是 `true`，但 React 的 `expanded` 一直是 `false` ——
浏览器不会对"已经在上面的指针"补发 mouseenter。
每次要展开岛都得**先挪开、等它离开、再移回来**。

### 坑 10：岛展开/收起时，窗口位置会变

展开时窗口变宽 → 主进程重新贴顶居中 → **窗口的 x 变了**。
用展开前量到的坐标去点展开后的按钮 → 点空（实测点不到喇叭）。
每次换算屏幕坐标前都要**重新读一次** `devBounds()`。

## 七、2026-11-24 凌晨肥鱼给的三件事（都已完成）

### 1. 真机验证的前置检查：屏幕锁着就不许跑

锁屏时 Windows 有一个全屏置顶的 `LockScreenBackstopFrame` 挡在所有窗口前面，
鼠标事件全被它吃掉 —— 岛收不到 hover、按钮点不到。
**看起来像"产品坏了"，其实是被锁屏挡住了。**

**已加**：`scripts/preflight.mjs` 的 `assertNotLocked()` ——
`LogonUI` 进程在跑就直接 abort，并说明原因（退出码 1）。
跟数据目录那条自检是同一类东西：**环境不对就别跑，跑了也是假结果。**

> ⚠ **但锁屏不是昨晚拖动测不出来的唯一原因**（更不是唯一原因）：
> 坐标体系那个坑（坑 8）也在起作用。**两个都得排掉。**

### 2. helper 的输出编码：中文乱码

helper 的 stderr 原来按 **GBK** 输出，主进程那边按 UTF-8 读 →
用户日志里是 `smtc: ��ѯʧ��:`，**媒体相关的错根本读不懂**。
已加 `Console.OutputEncoding = Encoding.UTF8`（实测输出"未知命令: badcmd"正常）。

### 3. helper 死因要分清"自己崩"和"被外部终止"

退出码 `4294967295`（-1）是**被外部杀掉**的典型值，不是自己崩的。
以前两种混在一行日志里，就分不清是不是被人关掉了。
现在分开写：`被外部终止（code=…，不是崩溃）` / `退出（code=…）`。

### 4. 解锁后确认岛在不在 —— **结论：在，是查法错了**

用户的正式版进程一直活着（主进程 57980），岛也在、可见。

肥鱼当时说"看不到任何可见窗口"，是因为**拿了一个 GPU 子进程去枚举窗口**
（方法错，不是产品问题）。教训写进《验证方法》第二十五节：
**认进程要先认父子关系。**
