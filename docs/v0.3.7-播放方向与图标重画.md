## 二、根因：不是图标画歪了，是**方向是猜的**

用户说"图标以及暂定播放标志不对"。分两层：

### 2.1 形状层：竖条画反了

截图放大后逐个数（`scripts/measure-play-direction.mjs` 量的是 SVG 几何数据，不是肉眼）：

| 图标 | 原来画的 | 实际渲染 | 标准形态 |
|---|---|---|---|
| 上一首 | 双左三角 + 竖条**在右** | `◀◀\|` | `\|◀◀` |
| 下一首 | 双右三角 + 竖条**在左** | `\|▶▶` | `▶▶\|` |
| 播放/暂停（两态） | 三角 + **一根**竖条 | `▶\|` | 跟"下一首"几乎一样 |

前两个是**镜像画反了**，第三个跟"下一首"撞脸 —— 三个都不合格。

### 2.2 方向层：读不到状态时只能猜

QQ 音乐新版内核（`qmbrowser.exe`）不再向 Windows 报告 SMTC 会话，
于是 `smtc current` 回「没有当前会话」——**歌名和播放状态都读不到**。

以前的界面逻辑是：`hasSession ? (playing ? 暂停 : 播放) : <两态图标>`。
读不到会话时显示两态图标，但那形状又跟"下一首"撞脸 →
用户看到的就是"图标不对"。

**这版的判据**（`src/shared/media-direction.ts`，有单测）：

```
读得到 SMTC 会话 → 以 SMTC 的 playing 为准（它连歌名都有，最权威）
读不到会话       → 用音频会话的**峰值**（那个进程有没有真的在出声）
两个都读不到     → null = 不知道 → 两态图标 + toggle 命令（**不猜方向**）
```

## 三、关键实测：会话状态**不能**当"在不在放"用

肥鱼给的判据是"用音频会话状态（Active = 正在播）"。**实测下来它不够准**：

| 判据 | 暂停方向延迟 | 播放方向延迟 |
|---|---|---|
| 音频会话的 **Active 状态** | **23.5 秒** | 1.1 秒 |
| 音频会话的 **峰值（peak）** | **1.9 秒** | 0.9 秒 |

> 会话 Active 只说明"这个进程还占着一条音频流"，**不代表此刻在出声**。
> 暂停后它要 23.5 秒才变 —— 拿它判方向，图标会滞后二十多秒。
> 真正实时的是**峰值**：出声时 > 0，暂停后掉到 0。

所以最终判据用峰值，Active 只作为"峰值读不到"时的退路，
并且**明确标记这是退路**（`audioPeakKnown=false`），界面知道自己在用一个慢的信号。

测量脚本：`scripts/probe-audio-latency.mjs`、`probe-pause-latency.mjs`、`probe-peak-latency.mjs`。

### 3.1 峰值怎么读（GUID 不凭记忆）

Core Audio 的 `IAudioMeterInformation`，在**会话对象**上 QI 出来：

```
IMMDeviceEnumerator → GetDefaultAudioEndpoint → Activate(IAudioSessionManager2)
  → GetSessionEnumerator → GetSession(i)
      → QI(IAudioSessionControl2) → GetProcessId + GetState
      → QI(IAudioMeterInformation) → GetPeakValue   ← 真正的"在不在出声"
```

GUID 与 vtable 顺序**全部抄自微软 SDK 头文件**（`audiopolicy.h` / `endpointvolume.h`，
从 win32metadata 仓库抓的原始头文件），不是凭记忆写的：

- `IID_IAudioSessionManager2` = `77AA99A0-1BD6-484F-8BC7-2C654C9A9B6F`
- `IID_IAudioSessionControl2` = `BFB7FF88-7239-4FC9-8FA2-07C950BE9C6D`
- `IID_IAudioMeterInformation` = `C02216F6-8C67-4B5B-9D00-D008E73E0064`

新增命令 `smtc audio` 会打出每条会话的 pid / 进程名 / 状态 / 峰值。

## 五、这轮踩到的四个坑（都写进《验证方法》第二十七节）

### 5.1 `devBounds()` 是 async，不 await 拿到的是 Promise

序列化出来是 `{}` → 坐标算成 `null` → **点击根本没发生**，
而脚本一路报"点了但状态没变"，看着像产品坏了。

### 5.2 `Get-Process` 里写了不存在的进程名，退出码是 1

即使加了 `-ErrorAction SilentlyContinue` 也是 1 → `execFileSync` 见到非 0 就抛错
→ 脚本误判成"一个音乐软件都没有"，直接退出，测都测不了。
**后面要补 `; exit 0`。**（这条让旧的 `measure-media-real.mjs` 一直误报。）

### 5.3 图标节点在鼠标底下被换掉 → 岛自己收起

状态一变就从 `PauseIcon` 换成 `PlayIcon`，那是**两个不同的 `<svg>` 节点**，
旧的被删、新的建在同一位置 —— 浏览器把这报成 mouseout，
岛于是以为鼠标移走了 → **400ms 后自己塌掉**。

用户看着就是"点了一下，岛没了"。这是我这一版**引入**的（以前图标不变，没这个问题）。

修法：**三个形态合并成一个组件** `PlayPauseGlyph`，`<svg>` 永远是同一个节点，
只换里面的 path/rect。单测锁住（`icons-shape.test.ts`）。

> 教训：动态图标不能按"整个 svg 换掉"的方式实现，除非那个按钮不在鼠标底下。

## 六、歌名的兜底：**读音乐播放器主窗口的标题**（追加）

用户原话还有「音乐还是不显示」。肥鱼当时定的是"歌名有就显示、没有就不显示"，
并且判断"你现在托盘里没窗口，读窗口那条路也不通"。

**实测：窗口是在的，而且它的标题就是「歌名 - 歌手」。**

```
class='QQMusic_Daemon_Wnd'  title='东风破 - 周杰伦'
class='TXGuiFoundation'      title='Bad (鼓点进行曲）'
```

切歌立刻跟着变（`scripts/probe-window-title.mjs --cut`，按一次「下一首」）：

```
切之前="觉悟 (古风带感版) - 混音太子"
切之后="东风破 - 周杰伦"
标题跟着歌变了 = true
```

**这不是 hack 出来的巧合** —— 播放器的主窗口标题栏**本来就在显示「歌名 - 歌手」**，
我们只是去读它。

### 6.1 怎么认主窗口（不能靠猜）

QQ 音乐同时开着十几个窗口：「播放模式选择」「播放队列」「TXMenuWindow」……
挑错了就会显示"播放队列"。所以按**类名**认：`QQMusic_Daemon_Wnd`。

> 标题会变，类名不会 —— 类名才是认窗口的稳定依据。

### 6.2 优先级

```
SMTC 读得到歌名 → 用 SMTC（连播放状态都有，最权威）
读不到          → 用窗口标题兜底（播放状态由音频会话给）
两个都读不到    → 歌名区空着（不显示假的）
```

### 6.3 ⚠ 这里踩到一个**看不出���**的错

加了兜底以后，歌名出来了、方向图标也对，但 `titleSource` 那一栏**永远是空的**。

原因：helper 发的是 `titleSource: "window-title"`，主进程认的是 `"window"` ——
**两边用词不一致**。

这个错从现象上看不出来（歌名照常显示、方向也大体对），
只能靠"两边用同一个词"这条规矩 + 断言来防：

- `src/main/media-protocol.test.ts`：**helper 发的字段名/值，主进程都得认**（协议一致性测试）
- 主进程现在**两种写法都认**（`'window'` 和 `'window-title'`），多一层保险

### 6.4 还有一条：方向必须跟着歌名来源走

加了兜底以后，`hasSession` 变 true 了，而方向逻辑原来只看 `hasSession`：

```ts
if (media.hasSession) return media.playing   // ← 错了
```

歌名来自窗口标题时，SMTC 的 `playing` 是**空的**（读不到），
拿它当方向会**永远是"暂停"** —— 歌名有了、方向却错了。

改成按 `titleSource` 选来源（`src/shared/media-direction.ts`，有单测）：

```ts
if (media.titleSource === 'smtc') return media.playing
return media.audioPlaying
```

## 七、这轮的教训

1. **「Active 状态」不等于「在出声」** —— 状态名会骗人，**峰值不会**。
   任何"这个程序现在在干嘛"的判据，都要拿**实际输出**去对，不能拿状态位。
2. **图标方向靠猜 = 一定错**。用户能一眼看出来，比功能坏还糟。
3. **动态图标别换整个 svg 节点** —— 尤其在鼠标底下。
4. **脚本自己的 bug 会伪装成产品 bug**：await 漏了、退出码没管，
   看起来都是"功能不工作"。
5. **两边用同一个词**（helper 与主进程的协议）—— 人记不住，要靠测试。
6. **"读不到"有两条路**：官方接口读不到时，**看看界面上本来就在显示什么**
   （播放器的主窗口标题就是「歌名 - 歌手」）。
7. **验证时先确认测的是哪个实例** —— 两个岛重叠时，鼠标命中谁是不确定的。

## 八、0.3.9 追加：音量滑条"一点就消失"（真 bug）

这条是在**打包版验包**时暴露的，而且**早就在 0.3.6 里了** —— 只是被"两个岛重叠"
掩盖住了（见下）。

### 8.1 现象

按住滑条开始拖 → **滑条当场消失** → 拖不动。
（之前 0.3.6 的验收是"真机拖动 7/7 全过"，但那时机器上还有用户那份 0.3.6，
两个岛完全重叠，鼠标点屏幕坐标时命中谁不确定。）

### 8.2 根因：click 事件冒泡

岛容器有个规则：「滑条开着的时候，点岛别处 = **收起滑条**」。

滑条只拦了 **pointer 事件**的冒泡（`e.stopPropagation()`），
但 **click 是另一个事件** —— 按下 + 松手产生的 click 照样冒泡到岛容器，
于是滑条刚被按住就被收走。

修：滑条同时拦 `pointerdown` 的 `nativeEvent` 和自己的 `onClick`。

```tsx
onPointerDown={(e) => { e.stopPropagation(); e.nativeEvent.stopPropagation(); ... }}
onClick={(e) => { e.stopPropagation() }}
```

### 8.4 最要紧的一条：**验包不许用 setup.exe 装**

electron-builder 的 NSIS 安装器会**按 appId 卸载已安装的旧版本** ——
**即使你用 `/D=` 指定了另一个目录**，它卸的是"注册表里记着的那个旧安装"。

我这次用它装到 `.tmp\pkg038`，结果把用户自己装的那份 0.3.6 卸了
（`E:\tomato-clock` 变空，用户的 5 个进程也没了；数据 `%APPDATA%\pomodoro` 完好）。

**正确做法：验包用「免安装单文件版」** —— 它不写注册表、不卸载任何东西、
不碰用户的任何目录，功能与安装版完全一样。

> 这跟《验证方法》第二十六节那条规矩同源：
> **对照实验只允许在自己起的临时实例里做，绝不许碰用户正在使用的任何程序。**
> 这一条是它的具体化：**安装器也算"碰"**。
