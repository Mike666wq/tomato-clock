## 二、行为规格（照这个写测试）

### A. 基本计时

| # | 行为 | 期望 |
|---|---|---|
| A1 | 启动后默认状态 | `focus` 阶段，剩余 = 专注时长，`running=false`，显示「准备开始」 |
| A2 | 开始 → 到点 | 剩余归零时进入下一阶段，写一条 `completed=true` 的记录 |
| A3 | 暂停 → 恢复 | 剩余时间不跳；`pausedSec` 累计暂停时长；`actualSec` **不含**暂停 |
| A4 | 暂停时改时长 | 当前段不变（`segmentTotalSec` 冻结），下一段生效 |
| A5 | 运行中改时长 | 同上：当前段不动，圆环分母不跳 |
| A6 | 未开始时改时长 | **立刻生效**（剩余和总长一起变） |
| A7 | 连续暂停/恢复 5 次 | `pausedSec` 是 5 次之和，误差 ≤ 1 秒 |

### B. 阶段流转

| # | 行为 | 期望 |
|---|---|---|
| B1 | 专注完成（第 1–3 轮） | → 短休 |
| B2 | 专注完成（第 4 轮） | → 长休，且长休时长取模板的 `longMin` |
| B3 | 长休完成 | → 专注，轮次计数继续（第 5 轮完成 → 短休） |
| B4 | 短休完成 | → 专注 |
| B5 | 休息段中途切模板 | 当前休息段时长不变；**下一个专注段用新模板** |
| B6 | `roundsBeforeLong` 改成 2 后 | 下一轮起按 2 计（已积累的轮次不清零） |

### C. 跳过与重置（**这三条是我定的，之前没定义**）

| # | 行为 | 期望 |
|---|---|---|
| C1 | 跳过专注段 | **写一条 `completed=false` 的记录**（原因=skipped），`focusRounds` **不增加**，进入休息段 |
| C2 | 跳过休息段 | 不写记录，直接进专注段 |
| C3 | 跳过之后的下一段 | **不自动开始**，即使 `autoStartNext` 打开（用户主动跳过通常是想换，不该被迫开局） |
| C4 | 重置当前段 | 只重置**当前这一段**：剩余回到整段、`pausedSec=0`、任务名清空、阶段不变、`focusRounds` 不变 |
| C5 | 暂停状态下重置 | 同 C4，且回到未开始状态 |

### D. 主题与任务名

| # | 行为 | 期望 |
|---|---|---|
| D1 | 启动后第一个专注段 | **挂上当前选中的主题**（已修，测试要守住） |
| D2 | 运行中切主题 | 当前段记录仍是旧主题；下一段用新主题 |
| D3 | 休息段里的任务名 | **不允许设置**（界面上禁用），记录里休息段的 `task` 为空字符串 |
| D4 | 编辑任务名后不提交直接走开 | 已输入的内容**保留在状态里**（不丢），下次编辑能看到 |
| D5 | 主题被归档后 | 历史记录仍显示当时的主题名（`topicNameSnapshot`），选择器里不再出现 |

### E. 持久化与恢复（**目前完全没有，这是最大的缺口**）

| # | 行为 | 期望 |
|---|---|---|
| E1 | 正在跑时正常退出 | 重新打开后**继续跑**（或至少恢复到退出时的剩余时间），不能凭空重来 |
| E2 | 正在跑时程序崩溃/断电 | 同上：下次启动按最后落盘的时刻恢复；若已过期，按"完成"处理并补一条记录 |
| E3 | 暂停时退出 | 恢复成暂停态，剩余时间保留 |
| E4 | 落盘频率 | 每秒一次太频繁；**状态变化时 + 每 30 秒一次**，且写入走原子写（tmp→rename） |
| E5 | 恢复时主题/模板 | 用**退出时那一份**（不能因为期间改过设置就把正在跑的段改掉） |
| E6 | 数据文件损坏 | 不崩，走默认值，并把坏文件改名备份 |

### F. 统计口径

| # | 行为 | 期望 |
|---|---|---|
| F1 | 「今日」归属 | 按**开始时间的本地日期**算；跨午夜的段算开始那天 |
| F2 | `actualSec` | = 实际跑起来的秒数（不含暂停），且用**冻结的段长**算（修 L1/L2） |
| F3 | 跳过/放弃的段 | **不计入**「今日专注分钟」，但计入「回合数」和打断率的分母 |
| F4 | 打断率 | 分母 = 该主题的回合数（含跳过/放弃），分子 = 有打断的 |
| F5 | 时区 | 一律本地时区，不碰 UTC 存储（存 ISO 带偏移，展示用本地） |

### G. 边界

| # | 行为 | 期望 |
|---|---|---|
| G1 | 时长为 0 或负数 | 拒绝并提示，落库前兜底 `max(1, x)` |
| G2 | 时长 180 分钟 | 显示 `180:00` 不截断，圆环按比例 |
| G3 | 系统休眠 2 小时后唤醒 | 若剩余已耗尽 → 立即完成该段并进下一段，**不要**再白给一整段 |
| G4 | 手工改系统时间 | 不崩；剩余时间可能跳变，接受，但要记日志 |
| G5 | 快速连点开始/暂停 10 次 | 状态一致，不出现 `running=true` 但计时不走 |
| G6 | 主窗口关闭（收托盘）时计时 | 继续走（已有，守住） |
| G7 | 两个窗口同时开着操作 | 状态一致（灵动岛和主界面都从同一状态机读） |

## 三、测试怎么落地

1. **`Timer` 是纯逻辑类**（只依赖 `Date.now()` 和 `setInterval`），**必须给它写单元测试**，用 vitest + fake timers。不测 UI。
2. 测试文件 `src/main/timer.test.ts`，先覆盖 A/B/C/D 五组，E 组单独（涉及 IO）。
3. 目前 `Timer` 里 `Date.now()` 是直连的，为了可测，抽一个 `now()` 注入点（默认 `Date.now`），测试里传假时钟。**这一条必须先做，否则 G3/G7 这类测不了。**
4. 每条测试的名字用规格编号：`it('C3 跳过之后不自动开始', ...)`——以后看测试名就知道测的是哪条规格。
5. 修 bug 的顺序：**L1/L2 → E（落盘恢复）→ C 组（跳过语义）→ 其余**。前两个是会丢数据和写错数据的。

## 四、UI 重做（这一轮先不动，逻辑修完再做）

我的判断：现在的问题不是"配色不好看"，是**信息结构和层次不对**——主界面像个设置面板。

具体毛病：
1. **四行堆叠**：模板条、主题条、状态行、导航栏，四行都在抢注意力，而真正的主角（时间）没有独占感。
2. **圆环太"网页"**：一条纯灰底轨 + 一根单色弧，没有质感，跟灵动岛那种精致感是两个东西。
3. **按钮平权**：开始/跳过/重置三个一样重，用户每次都要扫一眼找哪个是开始。
4. **缺少呼吸**：所有元素间距接近，没有主次。

方向（下一轮出两版稿让用户选）：
- **A 版·极简**：只留圆环 + 时间 + 当前任务 + 一个大的圆形主按钮；模板和主题收成圆环下方一行极小的文字胶囊，点开才展开。
- **B 版·质感**：保留信息量，但把圆环做成带渐变的厚描边 + 内发光，背景随阶段有极淡的径向光晕，数字更细更大（110–120px）。

两版都要遵守：颜色只从 `tokens.css` 取、不引组件库、深浅两套底色下都要清楚。

## 十八、E 组落盘方案（**待肥鱼拍板，暂未实现**）

第十一节要求"做之前先说打算怎么存"。这是我的方案。

### 18.1 存哪儿：单独文件，不塞进 `data.json`

建议 `%APPDATA%\pomodoro\running.json`。

理由：

1. `data.json` 里是"设置 + 全部历史记录"。每 30 秒重写它一次 = 每 30 秒把
   N 条记录重新序列化一遍，记录越多越慢，而且和用户提交记录的时刻撞在一起。
2. 崩溃恢复是**临时状态**：一段跑完就该没有它了。混在用户数据里，
   坏文件会污染真数据，反过来真数据写坏了也会把恢复状态一起弄坏。
3. E6 要求"文件损坏要改名备份不能崩"——独立文件才能单独做这件事，
   不牵动 `data.json`。

### 18.2 存哪些字段（全部是 `Timer` 里已有的量，不新造概念）

```ts
type RunningSnapshot = {
  /** 快照版本号，以后改结构时能识别旧文件 */
  v: 1
  phase: PhaseKind
  running: boolean
  /** 这一段的计划总长（冻结的那个，对应 segmentTotalSec） */
  segmentTotalSec: number
  /** 这一段已跑掉的秒数 */
  elapsedSec: number
  /** 这一段累计暂停秒数 */
  pausedSec: number
  /** 暂停时冻结的剩余秒数 */
  remainingSec: number
  /** 这一段开始时刻 */
  startedAt: string
  /** 最后一次落盘时刻——恢复时用它算"断电期间过了多久" */
  savedAt: string
  /** 这一段的任务名 */
  task: string
  /** 这一段挂的主题 */
  topicId: string | null
  /** 这一段用的模板 id（下一段用哪个模板的备份） */
  presetId: string
  /** 轮次与完成计数 */
  focusRounds: number
  completed: { focus: number; short: number; long: number }
}
```

### 18.3 落盘时机（E4）

- **状态变化时**：start / pause / resume / skip / reset / 阶段切换 → 立刻写
  （实现上用 300ms 防抖，避免连续变化时反复写）
- **运行时每 30 秒**一次心跳
- **退出时**写一次（`before-quit`）
- 全部走原子写：tmp → rename

### 18.4 恢复流程（E1 / E2 / E3 / E6）

1. 启动读 `running.json`
2. **读不到 / 解析失败** → E6：把坏文件改名成 `running.json.corrupt-<时间戳>`，
   走默认状态，不崩
3. 读到且 `running=true`：
   - 算"从最后落盘到现在过了多久"（墙钟差）
   - 剩余还够 → 恢复成运行中，剩余 = 剩余 - 流逝
   - 剩余已经耗尽 → 这一段在断电期间就跑完了 → **补一条"完成"记录**，
     然后进入下一段（E2 明写"已过期就补记一条完成"）
4. 读到且 `running=false`（暂停时退出）→ 恢复成暂停态，剩余保留（E3）
5. 恢复完成后**继续用同一个文件跟踪新的段**（心跳继续）

### 18.5 要加的接口（`Timer` 侧）

```ts
class Timer {
  /** 导出当前这一段的快照（纯数据，不做 IO） */
  getSnapshot(): RunningSnapshot
  /** 用快照恢复（启动时调用） */
  restore(snapshot: RunningSnapshot): void
}
```

`Timer` 本身**不碰文件**——IO 全在主进程：
主进程订阅 `timer.subscribe()` 触发防抖写，另起 30 秒 interval 做心跳，
`before-quit` 时再写一次。这样 `Timer` 仍是可测的纯逻辑类（E 组也能测）。

### 18.6 三个要你拍板的点

1. **关着应用的时候要不要继续计时？**
   E1 写的是"重新打开后继续跑（或至少恢复到退出时的剩余时间）"。
   真做到"关着也在计时"需要常驻托盘进程或系统级唤醒任务，
   成本和复杂度都高一个量级。**我建议按你括号里的第二档做：恢复到退出时的剩余。**

2. **断电期间跑完的那一段，补的记录用什么时间？**
   `startedAt` 用快照里的，`endedAt` 只能用"恢复时刻"（或者 lastSavedAt + 剩余秒数）。
   这条记录的时间戳会**不精确**（不知道它到底几点结束）。
   **能接受吗？** 或者干脆不补记，只在恢复时直接进下一段？

3. **跳过的段要不要进 `running.json`？**
   我的想法是**不要**：跳过是终态，没有"下次打开要接着跑"的语义，
   它当场就落进 `sessions` 了。省得快照里多一个字段。

> 另外提醒一个实现顺序：E 组要先做 `Timer.getSnapshot()` / `restore()`，
> 再做存储层；反过来做会逼着 `Timer` 去碰 IO，测试就没法写了。
