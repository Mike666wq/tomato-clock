## 二、缺陷明细

### D1｜并发保存设置会互相覆盖（读-改-写竞态）

**现象**
两个不相干的设置项同时保存，其中一个必然丢失。实测 4 轮全部丢：
第 4 轮要求 `uiTheme=ios` + `uiMode=dark`，磁盘上最后是 `uiTheme=paper` + `uiMode=dark`
—— **主题的改动被吞了**。用户看到的症状是「我改了主题，一会儿又变回去」「音量自己跳回来」。

**复现步骤**
1. 同一个 tick 里发两个请求：
   `settings.save({uiTheme:'ios'})` 和 `settings.save({uiMode:'dark'})`
2. 等 1 秒
3. 读 `data.json` → `settings.uiTheme` / `settings.uiMode`，其中一个不是刚设的值

**根因**
`src/main/index.ts:466` 的 `settings:save` 处理器是「读-改-写」：

```ts
ipcMain.on('settings:save', (_e, patch) => {
  void jsonStore.getSettings().then(async (current) => {
    const next = { ...current, ...patch }   // ← 基于旧快照合并
    await jsonStore.saveSettings(next)      // ← 写回整个 settings
```

两个请求各自读到**同一份旧快照**，各自合并自己的字段，然后各写回**整个** settings。
谁后写谁赢，赢的那份里另一方的字段是旧值 —— 改动凭空消失，且没有任何日志。

**打算怎么修**
主进程持有一份 settings 单例，写入串行排队：

- 加一个 `SettingsStore`：内存里存当前 settings，读走内存不读盘；
- 所有写操作进一条 Promise 队列（`this.queue = this.queue.then(...)`），保证不重叠；
- 队列里做「读内存 → 合并 patch → 更新内存 → 原子写盘」，写盘失败要回滚内存并记日志。

### D2｜每次缩放/拖动窗口都会重写整个 settings

**现象**
拖动窗口、改窗口大小，会让「刚刚改好的设置」变回去。频率比 D1 高得多 ——
拖一次窗口就是几十次 resize/move 事件。

**复现步骤**
1. 改主题
2. 拖动窗口（或改窗口大小）
3. 看主题有没有变回去

**根因**
`src/main/index.ts:287`：

```ts
const saveBounds = (): void => {
  const b = win.getBounds()
  void jsonStore.getSettings().then(async (settings) => {
    await jsonStore.saveSettings({ ...settings, window: {...} })  // ← 写回整个 settings
  })
}
win.on('resize', saveBounds)
win.on('move', saveBounds)
```

它读到的 `settings` 是一份**快照**。如果主题改动在这份快照之后才落盘，
这个写回就会把主题顶回旧值。跟 D1 是同一个根因（无串行化的读-改-写），
只是触发源是窗口事件而不是设置事件。

**打算怎么修**
同 D1：settings 单例 + 写入队列。另外 `saveBounds` 只应该写 `window` 这一个字段，
不要把整份 settings 重新写一遍（合并由队列里的合并逻辑做）。

### D3｜「今天」有两套口径

**现象**
跨零点的那一���番茄，主界面说「今天 0 个」，统计页说「今天 2 个」。
同一天、两个数字。

**复现步骤**
1. 造一条 `startedAt = 今天 23:50`、`endedAt = 明天 00:10` 的完成记录
2. 读 `records.summary()`（主界面用的）→ 按**结束时间**算今天 → 不算
3. 读 `stats.get()`（统计页用的）→ 按**开始时间**算今天 → 算
4. 两个数对不上

实测：主界面 = 0，统计页 = 1。

**根因**
两处口径不一致：

- `src/main/index.ts:117`（`buildSummary`）：`new Date(s.endedAt).toLocaleDateString('sv-SE') === today`
- `src/main/stats.ts:106`（`buildStats`）：`localDateKey(new Date(s.startedAt)) === todayKey`

规格里定的是**按开始时间算今天**（「今日归属按开始时间算」），
所以 `buildSummary` 用 `endedAt` 是错的，应该改成 `startedAt`。

**打算怎么修**
- `buildSummary` 改用 `startedAt`，和 `buildStats` 对齐；
- 「今天」的口径只留一处实现（抽一个 `todayKeyOf(session)`），两边都调它，
  以后不会再走偏；
- 补一条回归测试：造一条跨零点的 session，两个接口必须给出同一个数。

### D4｜主界面「今天 N 个」跨零点不刷新

**现象**
程序开着过了一夜，第二天早上主界面还显示昨天的「今天 3 个 · 75 分钟」，
统计页却已经是 0。两个页面同一个词、两个数。

**复现步骤**
1. 启动程序，界面显示「今天 N 个」
2. 跨过零点（改系统时间，或等到明天），期间不产生任何新记录
3. 主界面状态行不变，统计页（5 秒轮询）已经归零

**根因**
- 统计页是拉取式的：`src/renderer/pages/Stats.tsx:176` 每 5 秒 `stats.get()`
- 主界面的汇总是推送式的：`pushSummary()` 只在三处被调用
  （`index.ts:199` 落记录时、`457` 提交记录时、`589` 启动时）

没有定时刷新，所以不产生记录的时候数字永远停在昨天。

**打算怎么修**
- 主界面也改成拉取式：进页面拉一次 + 每 30 秒（或 60 秒）拉一次；
  顺带把 `records:summary` 的推送保留给「刚落了记录」的即时反馈。

### D5｜设置写入无校验，坏值直接把 data.json 写坏

**现象**
我给 `settings.save` 传了一个格式不对的值（`presets` 传成字符串而不是数组），
结果：**设置被原样写进了磁盘**，然后主进程在 `timerConfigOf(next)` 上抛异常，
界面上什么提示都没有，程序的模板条、主题行全空了。

**复现步骤**
1. `settings.save({presets: 'oops'})`
2. 看 `data.json` → `settings.presets` 已经是字符串
3. 看日志 → 有一条未捕获的 promise 异常，界面无任何提示

**根因**
- `settings:save` 对 patch 不做任何校验，直接 `{...current, ...patch}` 写盘；
- `jsonStore.saveSettings` 无条件写盘，没有"写之前先验一下"；
- handler 里 `void ...then(...)` 的异常没有 catch → 用户看不到；
- 写盘已经发生，回滚没有。

**打算怎么修**
- 写盘前做一次 settings 结构校验（字段类型、数组元素形状），不合法就拒绝并记日志 + 给界面一条提示；
- handler 里补 catch，把错误变成 `pushNotice('设置保存失败')`；
- 更稳的做法是写盘用「校验通过的新对象」而不是「原样 patch」。

### D6｜仓储层所有写共用同一个 `.tmp` 文件名（隐患，未复现）

**现象 / 风险**
`src/main/store/json-store.ts:109` 的 `writeRaw` 是「写 `.tmp` → rename」。
**所有**写操作（加记录、改记录、存设置、存窗口位置）都用同一个 `${target}.tmp`。
两个写同时进行时，内容可能互相搅在一起 → 文件变成非法 JSON。

另外 `readRaw`（`json-store.ts:91`）读不出 JSON 时，`catch` 里直接 `return defaultData()`，
**不记日志、不提示**。这意味着：文件一旦坏掉，程序会当成「全新安装」，
下一次任何写盘就会用默认设置覆盖掉它 —— **全部历史记录静默消失**。

**复现情况**
- 第一轮我确实看到一个坏掉的 `data.json`（尾部多了一个 `}`），但**那是我自己的测试脚本
  用了和程序一样的 `.tmp` 文件名**造成的，撞的是我的锅，不是程序的；
- 修正后用 80 次并发写压测，**文件始终是合法 JSON**，没能复现；
- 所以这是隐患，不算已确认的缺陷。但"读不出来就静默当默认数据"这条我认为是实打实的风险。

**打算怎么修**
- `writeRaw` 的临时文件名带上随机后缀（`${target}.${process.pid}.${counter}.tmp`），彻底避开撞名；
- `readRaw` 读失败时：改名备份 + 记 ERROR 日志 + 提示用户，**不要**静默返回默认数据；
- 仓储层加写入队列（和 D1 一起做）。

## 四、端到端脚本怎么跑

```powershell
# 1) 起一个独立实例（别用用户正式版，它正开着会撞单实例锁）
Remove-Item Env:ELECTRON_RUN_AS_NODE -ErrorAction SilentlyContinue
Start-Process node_modules\electron\dist\electron.exe `
  -ArgumentList '.', '--user-data-dir=<项目>\.tmp\e2e', '--remote-debugging-port=9222' `
  -WorkingDirectory <项目>

# 2) 跑旅程
node scripts\e2e-journey.mjs

# 3) 崩溃恢复那一段：强杀进程 → 重起 → 再跑
$env:E2E_STAGE='restore'
node scripts\e2e-journey.mjs
```

**两个环境坑（都是踩过的）**

1. `pnpm exec electron-vite dev -- --user-data-dir=...` 会报
   `CACError: Unknown option --userDataDir` —— electron-vite 的 cac 不接受这个开关。
   而 `ELECTRON_CLI_ARGS` 这条路在本次也没生效（`.tmp\e2e` 目录是空的，
   说明 Electron 根本没收到这个参数，仍然用了默认 userData，于是跟用户正在运行的正式版
   撞了单实例锁，**静默退出、退出码 0、没有日志**）。
   最后是用「直接起 electron.exe + 命令行带 `--user-data-dir`」解决的。
2. 打包版启动前必须 `Remove-Item Env:ELECTRON_RUN_AS_NODE`，
   这台机器预置了这个变量，Electron 会被强制当成纯 Node 跑。
